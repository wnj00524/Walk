# Operating the agentic workflow

## The coordinator prepares; the implementer executes

The coordinator checks the current repository and PLAN.md, reads the task's dependencies, confirms that required contracts and commands really exist, and marks one task READY. It fills in any backend/version-specific details discovered by earlier probes. WAITING cards are planning specifications, not unconditional permission to implement. If a card would exceed five implementation/test/config files or about 300 executable changed lines, split it before dispatch.

Every ready brief includes a user-visible outcome, read set, authorised file paths, expected interfaces, a small implementation sequence, acceptance checks with expected results, non-goals and stop conditions. Contract discovery belongs in a separately labelled probe/review task; it must not be hidden inside a low-capability implementation assignment.

An implementer states its plan, makes the narrow change, runs checks, updates documentation and supplies evidence. A reviewer starts with the actual diff and acceptance conditions. A fresh session of the same model is permitted; occasional use of a stronger model is an escalation choice, not a dependency of every task.

## Context budget

Root rules and orientation should remain short. Load one task and its read set, not all tasks. A task brief generated by the included tool contains root rules, that task, its dependency statuses, recent log rows and a bounded list of additional files to inspect. It deliberately does not inline every design document or source file.

Do not compress away exact units, error cases, data shapes or non-goals to save tokens. Conversely, do not repeat the complete product history in every prompt. Maintain a small CODE_GUIDE to locate ownership without scanning the entire repository.

## Ready check

Dependencies must be DONE; relevant interfaces must be fixed; task-specific source files must be known; required fixtures/checks must exist or be explicitly created by this task; no unapproved spend may be required; required execution environment must be available or the task must be split into implementation and later evidence. An owner-review task may become READY to perform its human approval, but an implementation task cannot pre-approve that outcome.

For remaining unresolved questions, issue a bounded research/probe task. A probe may conclude "not suitable" and be DONE as a completed investigation, while its acceptance gate remains BLOCKED. Do not treat completion of a failed investigation as acceptance of the technology. T012 is the explicit backend decision gate.

## Repairs and escalation

Allow at most two focused fixes of a failing task before a handoff. The recovery report includes expected vs actual behaviour, exact failure, minimal reproduction, changed files, and one next hypothesis. Do not ask another agent to "fix everything" or rewrite the repository. A coordinator may prepare a smaller diagnostic task, approve a different approach or seek a stronger review.

## Concurrency and trust

Default is serial execution. Once boundaries are stable, independent asset-tool tests and runtime logic may proceed in separate branches/worktrees. No shared output directories, simultaneous live scene edits or uncontrolled parallel asset submissions. One coordinator integrates task status/log updates and runs combined checks. Do not call code branches independent merely because their task titles differ.

Keep paid credentials out of untrusted branches and test jobs. Use host-level read/write scopes, network restrictions and approval controls where supported. AGENTS.md is a behavioural instruction, not an access-control mechanism. This starter pack does not implement an autonomous scheduler or host-side security enforcement.

## Handoff template

```text
Task and visible result:
Files changed:
Commands / exit codes / executed test counts:
Evidence that the reviewer can access:
Plain-English documentation updated:
Not run / limitations / remaining blocker:
Suggested next task (do not start it):
```

Each work session appends one DLOG row. PLAN status changes are explicit. Retain small reports under docs/evidence; publish large artifacts through the chosen review workflow. No automatic merge on the strength of an agent's final message.
