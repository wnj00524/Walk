## Outcome

The walker sees the approved placement data while distant batches are released within configured limits.

## Read set

Read the root rules/orientation/recent log, then the metadata read set and actual files being changed. Read dependency evidence when its result fixes a version or interface. Do not read every task.

## Allowed changes

Only the metadata paths, plus this task's evidence report, its relevant feature walkthrough, CODE_GUIDE.md, its PLAN.md row and one appended DLOG.md row. Directory scopes are not permission for unlimited changes. Do not change rules/contracts unless explicitly listed.

## Steps

1. Use spatially bounded instance batches rather than one whole-world batch; use actual approved materials/detail-level settings.
2. Keep scene changes on the main thread and discard stale results when the world/view epoch changes.
3. Test create/reuse/release behaviour with fixed records and record visual distance transitions.

## Acceptance

- Resident batch count stays within its configured bound during a synthetic route; returning recreates the same placements.
- Graphical capture shows objects touching the real terrain and no obvious whole-batch popping at the chosen provisional range.
- Run `python tools/project.py validate` and the existing helper tests. Explain the changed code in ordinary language and update its feature walkthrough.
- After the suite exists, run `python tools/check_game.py --suite vegetation` and affected regression suites. This command is introduced by T004; T003 uses the direct Godot script command while bootstrapping.

## Non-goals

No independent terrain scheduler or per-leaf collision.

## Stop conditions

Asset material/detail-level behaviour needs a separate repair task. Also apply AGENTS.md: stop after two failed focused repairs, for unapproved spend, unavailable required evidence, or when the coordinator must split the scope.
