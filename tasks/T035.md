## Outcome

Performance and resource-growth claims are supported by a moving route on identified hardware.

## Read set

Read the root rules/orientation/recent log, then the metadata read set and actual files being changed. Read dependency evidence when its result fixes a version or interface. Do not read every task.

## Allowed changes

Only the metadata paths, plus this task's evidence report, its relevant feature walkthrough, CODE_GUIDE.md, its PLAN.md row and one appended DLOG.md row. Directory scopes are not permission for unlimited changes. Do not change rules/contracts unless explicitly listed.

## Steps

1. Run the recorded warm-up and at least 30-minute measured route in an exported build, then return to known locations and include negative/large logical coordinates.
2. Collect real frame times, movement distance, available resident counters, process memory and cache bytes. Mark unavailable GPU metrics explicitly.
3. Analyse medians/percentiles and growth thresholds from TESTING.md; keep observations separate from target claims. Prepare bounded repair tasks for failures.

## Acceptance

- The route actually travelled through multiple newly generated regions; no stationary-success shortcut.
- Required continuity/resource criteria pass on named hardware or remain unresolved. Performance targets must be approved for that hardware before an overall pass.
- Run `python tools/project.py validate` and the existing helper tests. Explain the changed code in ordinary language and update its feature walkthrough.

## Non-goals

No invented FPS/RAM, average-only report or lowering visual quality without recording it.

## Stop conditions

Suitable runner/measurement tools are missing or thresholds are exceeded. Also apply AGENTS.md: stop after two failed focused repairs, for unapproved spend, unavailable required evidence, or when the coordinator must split the scope.
